# BridgeOS: Wire Protocol Specification

This document defines the wire protocol, framing rules, handshakes, and serialization formats for BridgeOS.

---

## 1. Framing Architecture

All data frames transmitted over stream transports (TCP/TLS or QUIC streams) follow a strictly bounded length-delimited format:

```
+-------------------+--------------------+-----------------------+
| Magic (4 bytes)   | Length (4 bytes)   | Payload (N bytes)     |
| ASCII "BRG1"      | Big-Endian u32     | Serialized Frame Body |
+-------------------+--------------------+-----------------------+
```

### Constraints:
- **Magic Header:** `0x42 0x52 0x47 0x31` (`"BRG1"`). Ensures immediate rejection of non-BridgeOS traffic.
- **Maximum Frame Length:** Default limit is **16 MB** (`16,777,216 bytes`). Frames exceeding this are dropped, and the connection is terminated immediately with an error.
- **Minimum Frame Length:** 1 byte (payload body).

---

## 2. Serialization Format

Frame payloads are serialized using **Postcard** (compact, zero-overhead versioned binary format) with standard serde derives, or canonical **JSON** during initial dev handshakes where transparency is beneficial.

Every payload begins with an envelope identifying the message type and schema version:
```rust
pub struct Envelope<T> {
    pub version: u16,
    pub message_id: u64,
    pub timestamp_ms: u64,
    pub payload: T,
}
```

---

## 3. Connection Handshake Flow

A connection must complete the three-way version and capability negotiation before any application data (clipboard, files, notifications) can be exchanged.

```
Initiator (Client)                              Responder (Server)
      │                                                │
      ├─────── ClientHello (Version, Caps, Nonce) ────>│
      │                                                │
      │<────── ServerHello (Agreed, Caps, Challenge) ──┤
      │                                                │
      ├─────── AuthResponse (Ed25519 Signature) ──────>│
      │                                                │
      │<────── AuthResult (Success / Denied) ──────────┤
      │                                                │
      │================= SECURE CHANNEL ===============│
      │                                                │
      ├<───────────── Application Data Messages ──────>┤
```

### Handshake Frames

1. **`ClientHello`**:
   - `protocol_version`: Major and minor version (e.g., `1.0`).
   - `node_id`: Public identity hash of the initiating device.
   - `device_name`: Human-readable device name (UTF-8, max 64 bytes).
   - `client_nonce`: 32 random bytes for session authentication.
   - `capabilities`: Bitflags indicating supported features (file transfer, clipboard, input).

2. **`ServerHello`**:
   - `agreed_version`: Selected protocol version compatible with client.
   - `node_id`: Public identity hash of the responder.
   - `device_name`: Human-readable device name of responder.
   - `server_nonce`: 32 random bytes generated by responder.
   - `negotiated_capabilities`: Intersection of client and server capabilities.
   - `challenge`: Salted challenge combining both nonces.

3. **`AuthResponse`**:
   - `signature`: Ed25519 signature over `SHA256(client_nonce || server_nonce || "BridgeOS-Auth-v1")`.

4. **`AuthResult`**:
   - `status`: `Success` or `Rejected(ReasonCode)`.

---

## 4. Control Messages

Once authenticated, peers exchange messages multiplexed across logical channels:
- `Ping` / `Pong`: Keepalive with monotonic timestamp.
- `Disconnect`: Graceful closure with reason code (`UserInitiated`, `Timeout`, `ProtocolViolation`).
- `Payload`: Subsystem data routed to registered handlers.
